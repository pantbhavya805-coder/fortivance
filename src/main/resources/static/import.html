Import Vendor Register

Load a bank's vendors, subcontractors, systems and business services from Excel. This is how a bank's own Fortivance instance is set up: once imported, incidents are traced and evidence is checked against the bank's real dependency map.

How it works
  1. Download the three templates below and open them in Excel. Each has one example row (a fraud-analytics vendor) you can keep or replace.
  2. Fill in one row per vendor, system and service. Vendors are matched by name and systems and services by code, so the files can refer to records already in the register (for example CNE or NimbusCloud Infra Pvt Ltd).
  3. Save each sheet as CSV: in Excel, File → Save As → CSV UTF-8 (Comma delimited). Semicolon-separated files from Excel's other regional settings work too.
  4. Check the files. Nothing is saved. Every problem is listed with its file and line, and you see exactly what would be created, updated or left unchanged.
  5. Import (Approver role). Everything is saved in one step, or nothing if any check fails. Nothing is ever deleted, and the import is recorded in the audit log.

Templates and files

1. Vendors

Direct vendors and their subcontractors (fourth parties): tier, data access, contract dates, regulatory scope.

↓ vendors-template.csv

2. Systems

The bank's applications, their recovery targets, and which vendors each depends on.

↓ systems-template.csv

3. Business services

What customers use, its impact tolerance and continuity plan, and the systems it needs.

↓ services-template.csv
Column reference

Columns marked * are required. Lists use ; between items. Dates: YYYY-MM-DD or DD/MM/YYYY. Yes/no columns accept yes, no, true, false, 1 or 0. Blank optional cells are saved as empty.

vendors.csv
name *Legal name; vendors are matched by name (not case-sensitive).
parent_vendorFor a subcontractor: the name of the direct vendor that uses it. Leave blank for direct vendors. Only one level is allowed.
service_category *Short category such as CLOUD_HOSTING, PAYMENTS, MESSAGING, IDENTITY_VERIFICATION.
service_descriptionWhat the vendor does for the bank (up to 500 characters).
risk_tier *CRITICAL, HIGH, MEDIUM or LOW.
materialMaterial outsourcing under the RBI Directions (yes/no, default no).
data_access *FINANCIAL, CUSTOMER_PII, INTERNAL or NONE.
outsourcing_scopeIN_SCOPE (default), EXCLUDED (for example SMS gateways) or UNDER_REVIEW.
scope_noteWhy the vendor is excluded or under review.
email_domainDomain the vendor sends notices from (for example vendor.com); used to spot spoofed incident notices.
contract_start, contract_end, last_assessed_on, next_review_dueDates. An overdue next_review_due adds to the vendor's risk score.
systems.csv
code *Short unique code such as CBS or FRM (capital letters, digits, - or _).
name *Full name of the system.
descriptionWhat it does.
criticality *CRITICAL, HIGH, MEDIUM or LOW.
owner_teamTeam responsible for the system.
rto_hours, rpo_minutesRecovery time and recovery point objectives (whole numbers).
vendorsVendors the system depends on, by name, separated by ;. They may be in vendors.csv or already in the register.
single_point_vendorsThose of the above with no alternative: a single point of failure.
services.csv
code *Short unique code such as SVC-PAY.
name *What customers call it.
descriptionWhat it covers.
customer_facingyes/no (default yes).
criticality *CRITICAL, HIGH, MEDIUM or LOW.
impact_tolerance_hoursLongest acceptable disruption, in hours.
bcp_plan_refReference of the business continuity plan, such as BCP-07.
business_ownerAccountable owner, such as Head of Payments.
essential_systemsSystem codes the service cannot work without (a failure makes it DISRUPTED), separated by ;.
supporting_systemsSystem codes whose failure only makes it DEGRADED.
